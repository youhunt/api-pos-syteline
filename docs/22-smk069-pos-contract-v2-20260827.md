# SMK069 POS Contract V2 — Receive to Blanket Customer Order

> **Status:** UAT-confirmed in tenant on 27 August 2026.
>
> This document is the current source of truth for the POS API contract and the Receive -> Temp -> Blanket Customer Order flow. It supersedes the earlier API semantics where POS supplied `conum` and `unit_price`.

## 1. Contract change

### POS sends

```text
custnum
order_date
cust_po
whse
coline
item
qty_ordered
u_m
```

### POS does not send

```text
conum
unit_price
```

SyteLine is responsible for both:

```text
conum       = R + YYMM + 5-digit running number
unit_price  = resolved from itemcustprice_mst
```

Example natural business payload:

```json
[
  {
    "custnum": "C000001",
    "order_date": "2026-08-06",
    "cust_po": "POS08270002",
    "whse": "MAIN",
    "coline": 1,
    "item": "AA00032",
    "qty_ordered": 1,
    "u_m": "CTN"
  },
  {
    "custnum": "C000001",
    "order_date": "2026-08-06",
    "cust_po": "POS08270002",
    "whse": "MAIN",
    "coline": 2,
    "item": "AA00032",
    "qty_ordered": 2,
    "u_m": "CTN"
  }
]
```

## 2. Identifier model

| Identifier | Example | Meaning |
|---|---|---|
| BatchId | `BATCH-20260827-002` | Receive batch idempotency key |
| cust_po | `POS08270002` | Original POS order / customer PO; groups lines into one atomic POS order |
| co_num | `R260822003` | SyteLine Customer Order number generated by Receive |
| created_co_num | `R260822003` | Compatibility/audit field set after Process; equals co_num in V2 |

Critical rule:

```text
POS cust_po != SyteLine co_num
```

## 3. Receive flow

Procedure:

```text
dbo.SMK069ReceivePosSalesJsonSp
```

Endpoint:

```text
POST /invoke/ue_SMK069TempSales?method=SMK069ReceivePosSalesJsonSp
```

The Mongoose IDO method still accepts a 10-element parameter array. Parameter 3 is `PayloadJson`, therefore the natural JSON array is serialized as a JSON string when sent to Mongoose.

Flow:

```text
raw JSON
-> ue_SMK069_pos_sales_inbound_mst
-> canonical mapping
-> customer/item/warehouse/U-M/terms validation
-> server-side pricing
-> atomic order validation by SiteRef + cust_po
-> generate co_num
-> ue_SMK069_temp_sales_mst, process_status = V
```

## 4. POS Transaction Data Contract V2

| Field | Type | Required | Rule |
|---|---|---:|---|
| custnum | String | Yes | max 7; customer_mst, cust_seq=0 |
| order_date | Date | Yes | YYYY-MM-DD |
| cust_po | String | Yes | max 25; original POS order |
| whse | String | Yes | must exist in whse_mst |
| coline | Integer | Yes | > 0; unique within SiteRef + cust_po |
| item | String | Yes | max 30; must exist in item_mst |
| qty_ordered | Decimal | Yes | > 0 |
| u_m | String | Yes | base U/M or item-specific conversion |
| conum | String | No input | generated by SyteLine |
| unit_price | Decimal | No input | resolved by SyteLine |

Server-derived defaults still used by the current receiver:

```text
SiteRef    = DEFAULT unless mapped otherwise
due_date   = order_date when no separate due date is supplied
terms_code = customer default, then validated in terms_mst
tax_code1  = customer default
exch_rate  = 1 in current same/base-currency flow
```

## 5. U/M validation

A line is valid when:

```text
payload u_m = item_mst.u_m
```

or an item-specific conversion exists:

```text
u_m_conv_mst.item = payload item
AND
(
  u_m_conv_mst.from_u_m = payload u_m
  OR
  u_m_conv_mst.to_u_m = payload u_m
)
```

One invalid line makes the whole `SiteRef + cust_po` order Error.

## 6. Warehouse validation

`whse` is mandatory and must exist in `whse_mst` for the target site. The supplied value is preserved into temp and the Customer Order.

## 7. Unit price resolution

The receiver selects the latest effective customer/item price row:

```sql
SELECT TOP 1 ...
FROM dbo.itemcustprice_mst
WHERE site_ref = @SiteRef
  AND item = @item
  AND cust_num = @custnum
  AND effect_date <= @order_date
ORDER BY effect_date DESC, RecordDate DESC;
```

Current implemented pricing hierarchy:

1. If `cont_price <> 0`, use `cont_price`.
2. Otherwise use the highest applicable quantity-break price where `brk_qty <= qty_ordered` and the break price is non-zero.
3. If no usable price can be resolved, the order is invalid.

Confirmed UAT data:

```text
Customer       C000001
Item           AA00032
Item U/M       CTN
Effect date    2026-07-30
cont_price     80000
order_date     2026-08-06
resolved price 80000
```

## 8. Auto-generated co_num

Format:

```text
R + YYMM + 5-digit running number
```

Conceptual example:

```text
R260800001
```

Actual UAT result:

```text
R260822003
```

The running suffix continues from existing tenant data. Receive uses an application lock so concurrent calls do not allocate the same number.

## 10. Process Blanket Customer Order V2

Procedure:

```text
dbo.SMK069ProcessCustomerOrderSp
```

**Important semantic change:** parameter name `@SourceCoNum` is retained for backward compatibility, but in V2 its value is the **generated staging co_num**, not the POS order number.

Example:

```text
@SiteRef     = DEFAULT
@SourceCoNum = R260822003
@CustSeq     = 0
```

Process must not generate another number.

Final mapping:

```text
temp.co_num         = R260822003
temp.cust_po        = POS08270002

co_mst.co_num       = R260822003
co_mst.cust_po      = POS08270002
co_mst.type         = B

coitem_mst.co_num   = R260822003
co_bln_mst.co_num   = R260822003

temp.created_co_num = R260822003
temp.process_status = P
```

One staging line produces one `coitem_mst` row and one `co_bln_mst` row.

Blanket line requirements include:

```text
stat               = O
allow_on_pick_list = 0
blanket_qty        = staging qty_ordered
cont_price         = staging unit_price
u_m                = staging validated u_m
whse               = staging whse
```

## 11. Transaction safety

Receive and Process use caller-safe transaction handling for Mongoose/IDO:

```text
no outer transaction -> procedure owns transaction
outer committable transaction -> use SAVE TRANSACTION
outer uncommittable transaction -> rethrow original error; caller owns rollback
```

This prevents the earlier transaction-count mismatch and preserves atomic order creation.

## 12. Error Processing form controls

The Error Processing form is a controlled processing boundary.

Required behavior:

```text
New/Create = disabled
Copy       = disabled
Delete     = disabled
Process/Reprocess = controlled action
```

Invalid Receive rows remain in inbound and do not enter temp.
